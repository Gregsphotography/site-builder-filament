# Canonical numbers and historical compatibility

Numeric policy: `legacy-compatible-exact-v1`. Accepted values retain their existing canonical bytes and digests. The MIT mmccook backend is pinned to the reviewed 1.0.0 release; an upstream algorithm update requires a new compatibility review. Its output is guarded against trailing-zero loss and decimal rounding: its float token must equal PHP shortest round-trip serialization normalized to ECMAScript exponent thresholds. PHP `serialize_precision=-1` is required; the library never changes that setting.

Affected values such as float `10.0`, `1e20`, or over-precise decimals are refused before a new digest or document write. Integer `10`, ordinary decimal layout values, string identities and existing compatible digests retain their meaning. 238 independently checked JavaScript numeric vectors exercise accepted and refused cases, alongside 317 compatible legacy vectors and a refused inherited collision. This deliberately restricts supported numbers; it is not a claim to accept every RFC 8785 number.

Historical document decoding and raw native export preserve original values and stored bytes. Hash-dependent edit, import, history, clipboard, publication and setup operations refuse affected data rather than trusting a colliding historical digest. No automatic rehash or database migration occurs. Before upgrading a real host, run the read-only numeric preflight in a disposable copy, retain a coherent code/database/media backup, and review every affected JSON value. Do not cast opaque IDs or exact amounts to float. Any conversion to a string or other representation requires explicit schema/content review and reapproval of affected publication/history state. Existing SQL/native backups remain available; full corrected-number support needs a separately versioned migration.

See [RFC 8785 numeric serialization](https://www.rfc-editor.org/rfc/rfc8785#section-3.2.2.3) and [PHP JSON serialization settings](https://www.php.net/manual/en/function.json-encode.php).
